五、第一版上下文方案

不要一开始就实现复杂上下文算法

最简单可靠的做法：每次发送时查询最近 N 条消息，组装 Prompt。

用户 发送消息
查询最近 N 条消息（如 20 条）
组装 Prompt（System + History + 当前问题）
调用 AI
保存 AI 回复
ServiceImpl 核心逻辑 
List<ChatMessage> history =
        messageMapper.selectRecentMessages(conversationId, 20);

List<AiMessage> messages = new ArrayList<>();
messages.add(systemMessage);                // 系统设定
for (ChatMessage message : history) {
    messages.add(convert(message));         // 历史消息
}
messages.add(userMessage);                   // 当前问题
这就是一个可用的 AI 聊天了。先把链路跑通，再谈优化。

进阶：历史摘要 + 最近消息

会话拉长后，全量历史会让 token 成本与延迟持续上涨。升级做法是历史摘要 + 最近消息：把早于窗口的历史压缩成一段摘要（Conversation Summary），窗口内的最近消息原样保留，调用 AI 厂商时按"角色设定 + 历史摘要 + 最近消息 + 当前问题"组装 messages。

System Prompt
历史摘要
最近 N 条消息
当前问题
调用 AI 厂商时的 messages 数组 
[
  { "role": "system",   "content": "你是匿名聊天助手。\n\n[历史摘要]\n用户是一名 Java 后端开发人员，正在开发匿名聊天系统，使用 Spring Boot + MySQL + Redis。" },
  { "role": "user",      "content": "最近的某条消息" },
  { "role": "assistant", "content": "对应的 AI 回复" },
  // …… 最近 N 条消息 ……
  { "role": "user",      "content": "当前问题" }
]
消息数 超过阈值（如 50 条）时，把窗口外最早的消息交给模型生成摘要
摘要与最近消息分开放：conversation.summary 字段 + chat_message 表
再次调用 AI 时， 按"角色设定 + 历史摘要 + 最近 N 条 + 当前问题"组装 messages
每轮对话结束后滚动更新摘要
ServiceImpl 核心逻辑 
String summary = conversation.getSummary();        // 历史摘要（滚动更新）
List<ChatMessage> recent =
        messageMapper.selectRecentMessages(conversationId, 20);

List<AiMessage> messages = new ArrayList<>();
messages.add(AiMessage.system(
        systemPrompt + "\n\n[历史摘要]\n" + summary));
for (ChatMessage message : recent) {
    messages.add(convert(message));        // 最近消息
}
messages.add(userMessage);                  // 当前问题
效果：模型既能看到久远上下文（摘要），又能拿到最近细节（最近 N 条），token 成本稳定在可控区间。

六、Streaming 流式输出

聊天体验的关键，放在基础链路跑通之后

普通模式（一次性返回）

用户发送 → Spring → AI
等待 5 秒 ↓
一次性返回：
"你好，我是AI，很高兴认识你..."

用户长时间看着空白等待，体验较差。

流式模式（逐字输出）

用户发送 → Spring → AI
↓
"你好"
↓
"你好，我是"
↓
"你好，我是AI，很高兴认识你▌"

前端看到的就是 ChatGPT 那种打字机效果。

通信方式：SSE（Server-Sent Events）。AI 回复是"服务端 → 客户端"的单向流，SSE 基于 HTTP、浏览器原生 EventSource 即可接收、断线自动重连，比 WebSocket 更轻，无需握手与额外协议。

前端 EventSource
POST /api/chat/ai/stream
Spring Boot · SseEmitter
AiProvider
AI 模型 API（stream）
data: 增量文本
前端逐段拼接 → 打字机效果
前端：EventSource 接收（Vue 示例） 
// EventSource 基于 GET；若需 POST 传参，可用 fetch + ReadableStream 流式读取
const es = new EventSource(`/api/chat/ai/stream?conversationId=${conversationId}&message=${encodeURIComponent(message)}`);

es.onmessage = (event) => {
    answer += event.data;          // 每段增量直接拼到回复气泡上
};
es.onerror = () => { es.close(); };   // 重连由 EventSource 内置处理
后端逐段落库，前端只负责拼字。流式推给前端的同时，后端把完整回复写入 chat_message，刷新后仍能看到完整对话。

2. 一次性对话：AiProvider 的真实实现

DeepSeekProvider.java 
@Service
public class DeepSeekProvider implements AiProvider {

    @Value("${ai.deepseek.api-key}") private String apiKey;
    @Value("${ai.deepseek.base-url}") private String baseUrl;
    @Value("${ai.deepseek.model}")   private String model;

    private final RestTemplate restTemplate = new RestTemplate();

    @Override
    public AiResponse chat(AiRequest request) {
        // 1. 组装请求体（OpenAI 兼容格式）
        Map<String, Object> body = new HashMap<>();
        body.put("model", model);
        body.put("messages", request.getMessages());
        body.put("temperature", request.getTemperature());

        // 2. 设置鉴权头
        HttpHeaders headers = new HttpHeaders();
        headers.setContentType(MediaType.APPLICATION_JSON);
        headers.setBearerAuth(apiKey);     // Authorization: Bearer xxx

        HttpEntity<Map<String, Object>> entity =
                new HttpEntity<>(body, headers);

        // 3. 发起 POST
        String url = baseUrl + "/chat/completions";
        Map resp = restTemplate.postForObject(url, entity, Map.class);

        // 4. 解析回复：choices[0].message.content
        List choices = (List) resp.get("choices");
        Map first = (Map) choices.get(0);
        Map message = (Map) first.get("message");
        return AiResponse.of((String) message.get("content"));
    }
}
关键就在 messages 数组：role 只有 system / user / assistant 三种，把历史消息按顺序放进去，模型就能"记住"上下文。

4. 流式对话：逐字输出（SSE）

后端用 SseEmitter + WebClient 把模型返回的增量文本一段段推给前端：

ChatController.java 
@PostMapping(value = "/api/chat/ai/stream",
        produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter stream(@RequestBody SendRequest req) {
    SseEmitter emitter = new SseEmitter(0L);   // 不设超时
    aiService.chatStream(req.getConversationId(), req.getMessage(), emitter);
    return emitter;
}
AiService 流式实现（WebClient） 
WebClient client = WebClient.builder()
        .baseUrl(baseUrl)
        .defaultHeader("Authorization", "Bearer " + apiKey)
        .build();

client.post()
    .uri("/chat/completions")
    .bodyValue(body)
    .accept(MediaType.TEXT_EVENT_STREAM)
    .retrieve()
    .bodyToFlux(String.class)          // 每个 SSE 事件一个字符串
    .subscribe(chunk -> {
        // 解析 delta.content 并推给前端
        emitter.send(SseEmitter.event().data(content));
    }, emitter::completeWithError, emitter::complete);
前端只需用 EventSource 监听 message 事件（见第六节）即可实时拼字，得到"打字机"效果。

十五、用户自建角色与角色聊天

让每个用户都能创建自己的 AI 角色，保存上下文，长期与角色对话

在 ai_agent 表上增加归属与展示字段（见 14 节数据库），区分系统角色与用户自建角色：

自带 API Key：用自己的 Key 调厂商

用户可以在创建角色时绑定自己的厂商 API Key，系统用该 Key 调用模型，费用由用户承担、不占用系统配额。

字段说明

apiBaseUrl厂商 base-url，留空 = 系统默认
apiKey用户自己的 Key，留空 = 系统默认 Key
Key 安全：apiKey 加密后写入 ai_agent.api_key_enc（AES / Jasypt），不存明文；列表与编辑接口脱敏返回（只显示尾号），Key 一经保存不可再回显原文。前端表单也只做"覆盖 / 清空"操作，不展示旧值。
调用优先级：角色自带 Key > 系统默认 Key（application.yml）。系统角色、未填 Key 的角色继续走系统默认配置，行为不变。示例见下方"与角色聊天" ChatService 第 3 步。

@Component
public class CryptoService {

    private final SecretKey aesKey;   // 由环境变量 AES_KEY 初始化，不硬编码

    public String encrypt(String plain) {
        // AES/GCM 加密 → Base64 密文，写库 api_key_enc
        return base64(aesGcm.seal(plain.getBytes(), aesKey));
    }
    public String decrypt(String cipher) {
        // 解密只在调用 AI 前执行，结果用完即弃
        return new String(aesGcm.open(unbase64(cipher), aesKey));
    }
}
调用顺序：数据库读取密文 → crypto.decrypt() 解密 → 放进 AiRequest → 调厂商 API → 解密结果用完即弃（不留存、不打日志）。

用户 Key 的额度、安全与限流

风险表现应对方案
Key 额度耗尽厂商返回 quota_exceeded / 401 / 429捕获错误并提示"你的 Key 额度已用完，请到角色编辑页更新"；失败计次，连续失败自动停用该角色 enabled，避免每条消息都报错
安全问题（Key 泄露）Key 被他人盗用，产生盗刷AES 加密落库 + 接口脱敏；提供一键"轮换 / 重置 Key"；异常调用（频次突增 / 异地）自动冻结该角色并通知用户
限流单用户高频调用挤占资源 / 触发厂商限流按用户维度限流（ai:chat:rate 每分钟 N 次，Redis 计数）；再按角色 Key 维度限流；超限返回 429 提示稍后再试
调用前：Redis 检查用户限流 + 角色 Key 健康状态（是否已停用）
调用失败：区分 401（Key 失效）/ 402（额度耗尽）/ 429（限流）
连续失败：计数超阈值 → 自动停用角色 / 通知用户更新 Key
限流 + 额度异常处理（AiServiceImpl） 
// 1. 调用前：用户维度限流（Redis 滑动窗口计数）
if (!rateLimiter.tryAcquire(userId, 60)) {
    throw new BizException("请求过于频繁，请稍后再试");
}

// 2. 调用厂商，捕获 Key 相关错误
try {
    reply = aiProvider.chat(req);
} catch (ProviderException e) {
    // 401 = Key 失效 / 402 = 额度耗尽 / 429 = 限流
    if (e.isQuotaExceeded() || e.isKeyInvalid()) {
        failCounter.incr(agentId);
        if (failCounter.get(agentId) >= 5) {
            agentService.disable(agentId);   // 连续失败自动停用角色
        }
    }
    throw e;
}
原则：用户 Key 的额度、安全、限流责任尽量落在角色 / 用户维度，把影响隔离在角色自身，不波及系统 Key 与其他用户。

ChatService.chat 核心逻辑 
@Override
public String chat(String conversationId, String message) {
    // 1. 取会话绑定的角色
    Conversation conv = conversationMapper.getById(conversationId);
    AiAgent agent = agentMapper.getById(conv.getAgentId());

    // 2. 组装 messages：角色设定 + 保存的上下文 + 当前问题
    List<AiMessage> messages = new ArrayList<>();
    messages.add(AiMessage.system(agent.getSystemPrompt()));  // 角色人格
    messages.addAll(loadHistory(conversationId, 20));        // 上下文
    messages.add(AiMessage.user(message));                     // 当前消息

    // 3. 组装请求：角色自带 Key 优先，否则走系统默认
    AiRequest req = AiRequest.of(agent.getModel(), messages);
    if (StringUtils.hasText(agent.getApiKeyEnc())) {
        req.setApiKey(crypto.decrypt(agent.getApiKeyEnc()));  // 用户自己的 Key
        req.setBaseUrl(agent.getApiBaseUrl());
        req.setProvider(agent.getApiProvider());
    }
    String reply = aiProvider.chat(req);

    // 4. 保存这条消息与回复，供下次继续
    messageService.saveUser(conversationId, message);
    messageService.saveAi(conversationId, reply);
    return reply;
}
角色设定（systemPrompt）存在角色表，不随消息重复存。同一个角色可以开多个会话，每个会话独立保存上下文、互不串扰。

AgentController.java 
@RestController
@RequestMapping("/api/ai/agent")
public class AgentController {

    // 1. 权限点校验：没有 ai:agent:create 直接 403
    @PostMapping("/create")
    @PreAuthorize("hasPermi('ai:agent:create')")
    public R create(@RequestBody CreateAgentRequest req) { ... }

    // 2. 删除：权限点 + 归属校验（只能动自己的，管理员除外）
    @DeleteMapping("/{id}")
    @PreAuthorize("hasPermi('ai:agent:delete')")
    public R delete(@PathVariable Long id) {
        AiAgent agent = agentService.getById(id);
        if (!isAdmin() && !agent.getUserId().equals(loginUserId())) {
            return R.fail("无权删除他人创建的角色");
        }
        return agentService.remove(id);
    }
}
前端隐藏按钮 ≠ 安全：真正的权限控制必须落在后端，前端只是体验层，直接调接口也要被拒。
